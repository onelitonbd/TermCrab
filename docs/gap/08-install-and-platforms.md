# Install, platforms, and distribution — gap report

TermCrab's packaging is correct and its distribution story is a single 172-line bash script. `package.json` is a well-formed, dependency-free, ESM, `bin`-declaring npm package (`package.json:3`, `:23`, `:27`) with `engines.node >= 20.10` (`:25`); the web UI is served out of the same install (`src/gateway/server.ts:1811` reading `uiDir()` → `src/core/paths.ts:81`→`:82`), and `findPackageRoot()` (`src/core/paths.ts:13`–`31`) walks up to `package.json` with `name === "termcrab"` in four hops from `dist/src/core/`, so a `npm i -g` layout resolves correctly. That is the good news, and it is not nothing — it is roughly 6 hours of work that has already been done. Everything else in this cluster is missing or wrong. There is **no npm publish** (no `private: true`, no `publishConfig`, no release workflow — `.github/` does not exist), **no Dockerfile, no compose file, no systemd unit, no launchd plist, no Nix expression, no `.deb`/`.rpm`/AppImage** (verified: `find` over the whole repo excluding `node_modules` returns zero matches for all of those patterns), **no uninstall path in code or docs**, **no backup command despite a `config-backups/` directory that `ensureLayout` creates on every invocation** (`src/core/paths.ts:96`), and **no rollback**. On platforms, TermCrab is genuinely excellent on Android/Termux — the bionic guard (`src/mobile/bionic.ts:80`), the supervisor (`src/mobile/supervisor.ts:14`), and the Termux:Boot script (`src/mobile/boot.ts:17`) are real, working, and correctly solve a problem OpenClaw does not have — and genuinely absent everywhere else: there is no macOS story, no Windows story, and no documented support statement for either. OpenClaw ships 21 install/platforms pages including systemd/LaunchAgent/Scheduled Task service installs, a containerised Gateway with health checks and observability, a 27 KB backups page with Litestream replication, and a 42 KB Node-compatibility page that documents the exact SQLite floor and *why*. The single most damaging item in this report is not a missing feature: it is `README.md:60`, which tells users to curl `install.sh` from a **work branch** (`arena/01a0ec99-claw`) rather than from `main` as `install.sh:3` itself documents.

## Clusters

### Packaging is correct; distribution is a git clone

The single most common failure mode for a Node CLI is getting `package.json` wrong — missing `files`, shipping `src/` instead of `dist/`, forgetting the `bin` chmod. TermCrab has none of those problems. `files` (`package.json:27`) lists `dist/src`, `skills`, `ui`, `docs`, `install.sh`, `README.md`, `LICENSE`, `CHANGELOG.md`; `copy-assets.mjs` chmods the bin to `0755` after `tsc`; `findPackageRoot()` (`src/core/paths.ts:13`–`31`) tolerates being compiled into `dist/`; and because `ui/` is both git-tracked and in `files`, the web UI is genuinely available from any install layout.

The problem is the other half. Nothing publishes this package. There is no `publishConfig`, no `private: true` guard, and `.github/` does not exist — so there is no release workflow that *could* publish. `checkForUpdate` reads `api.github.com/repos/onelitonbd/claw/releases/latest` (`src/core/update.ts:44`) rather than an npm dist-tag, which tells you the intended distribution channel is the git clone, and `install.sh` implements exactly that. That is a legitimate choice for a Termux-first project where `npm i -g` pulls a large tree that Android users cannot install. It is a bad choice for everyone else, and it means `npm i -g termcrab` is undocumented and unverified.

Two consequences worth naming: `prepare: npm run build` (`package.json:39`) runs `tsc`, so `install.sh:94`'s `npm install` in a clone installs `typescript` + `@types/node` as devDependencies and builds. That means **every install pulls a compiler**, takes tens of seconds, and requires network access to the npm registry after the git clone succeeded. A prebuilt tarball would cut install time substantially.

### install.sh: what it does well, and the five things it gets wrong

Genuinely good, and better than most hand-written installers:

- Refuses to claim success without running the binary (`install.sh:145`–`:147`).
- Detects a shadowing older install and says so (`:149`–`:153`) — this is the failure mode that costs people hours.
- Handles both branch and tag installs, including the tag→detached-HEAD case (`:41`–`:47`, `:67`–`:73`, `:79`–`:88`).
- Refuses to overwrite a dirty tree without saying so (`:50`–`:64`).
- Writes a self-locating shim and drops a second one in `$PREFIX/bin` on Termux (`:126`–`:132`), avoiding PATH surgery.

Wrong:

1. **Zero flags.** `install.sh` reads no arguments at all. `grep -n '\$@\|\$1\|\$2\|getopts\|shift'` matches only inside `write_shim`. There is no `--no-onboard`, no `--version`, no `--prefix`. OpenClaw has all three plus a 36 KB flag reference.
2. **`TCRAB_DEST` is half-implemented.** `DEST` (`:9`) is used for the clone, upgrade, and version print — but the shim's candidate list (`:106`–`:110`) is a hardcoded literal containing `$HOME/.local/share/termcrab`, `$HOME/.termcrab`, and two relative guesses. Install with `TCRAB_DEST=/opt/termcrab` and the clone lands in `/opt/termcrab` while the shim looks in four other places; the smoke test at `:145` then fires and the script aborts with "the termcrab command was written but did not run (is node on your PATH?)" — a message that points at the actual cause of nothing.
3. **Node provisioning is Termux-only.** `:16` requires `$PREFIX` *and* `$PREFIX/bin/pkg`. On a Debian box with no Node, the script exits at `:20` telling you to install Node yourself. This is the same shape as bug 2's failure: an advertised capability that only works in one environment.
4. **`git clean -fd` (`:63`) is unprompted and unconditional** on the upgrade path. The comment at `:59`–`:61` justifies it ("user data lives in `~/.termcrab`, not the install dir"), which is true, but any note file or patch a user dropped into the install directory is destroyed with no confirmation. One `say` line, or `clean -fd -n` first, would close this.
5. **The Node gate is looser than the declared gate.** `:24` tests `NODE_MAJOR -ge 20`, so Node 20.0–20.9 passes the installer but fails `package.json:25`'s `">=20.10"`. `npm install` only warns on an engine mismatch, so the install "succeeds" and the user finds out later. `src/mobile/doctor.ts:118` does the correct 20.10.0 comparison — the installer should use the same check.

| `src/mobile/doctor.ts:118` | `semverAtLeast(process.versions.node, '20.10.0')` | patch-accurate |
| `README.md:47`, `docs/TERMUX.md:13` | "Node >= 20.10", "Node ≥ 20.10" | prose |
| `package.json:36` CI (not wired) | Node 20 / 22 / 24 matrix (`ci/github-actions.yml`) | **major only** — Node 20 in the matrix means "20.x", including 20.0 |

OpenClaw's page is the counterexample: an exact `engines` expression, a per-line support table with Status and Notes columns, a documented runtime capability probe for the `node:sqlite` WAL bug, and prose explaining *why* each floor exists. TermCrab needs 10 lines of that, not 13 KB — the only floor it has is "20.10", and the only reason worth writing down is the global-`fetch` dependency (`src/core/update.ts:42`).

The `ci/github-actions.yml` Node 20 entry should be `20.10` or higher to match `engines`, otherwise CI proves compatibility for a range `package.json` rejects. (`ci/` is not wired into `.github/` — see report 09.)

### Init systems: three layers on Android, zero everywhere else

This is the clearest architectural split in the codebase. Android has no systemd, so TermCrab wrote a supervisor — and wrote it well: exponential backoff capped at 30 s (`src/mobile/supervisor.ts:22`, `:65`), backoff reset after a 60 s stable run (`:63`), stdout/stderr tee to a log file (`:46`–`:52`), and a `TCRAB_SUPERVISOR=1` sentinel (`:41`–`:43`) that lets the update path exit cleanly rather than racing a restart. The Termux:Boot script (`src/mobile/boot.ts:17`–`:33`) composes correctly with it: wake-lock, `TCRAB_HOME` export, `nohup node <bin> supervisor`.

Outside Android, none of that exists. A Linux user gets `termcrab gateway` in the foreground and Ctrl+C. A macOS user gets the same. The absence is total and verified — no `.service`, no `.plist`, no unit renderer anywhere in `src/`.

The cheapest correct fix is a `termcrab gateway install` that renders a systemd **user** unit (Linux) and a LaunchAgent (macOS) from the same `termcrab gateway run` command, plus `gateway status/stop/restart/uninstall`. Roughly 2–3 days, and it converts "runs if you keep a terminal open" into "runs".

### Backups: a directory that lies

`ensureLayout()` creates `~/.termcrab/config-backups` on **every** invocation (`src/core/paths.ts:96`), and `ensureLayout()` is called at the top of `loadConfig` (`src/core/config.ts:189`), `startGateway` (`src/gateway/server.ts:252`), and `saveConfig` (`src/core/config.ts:217`). Nothing ever writes to that directory. Verified: `grep -rn "config-backups" src/` returns only the creation.

Meanwhile `saveConfig` (`src/core/config.ts:216`–`:222`) is a bare `fs.writeFileSync` with no temp-file-and-rename, and `loadConfig`'s catch-all at `:211`–`:213` returns `defaults()` on a parse error. So a config truncated by a crash or a full disk silently becomes a working-looking default config with no provider, no token, and no Telegram — and the user is told nothing.

Against that, OpenClaw ships a 27 KB backups page with six distinct strategies (full archives with manifest verification, per-database SQLite snapshots with SHA-256 recheck, cold transcript backups, Git-backed incremental history, Litestream continuous replication, `sqlite3_rsync` pull replication), retention flags (`--keep-daily/weekly/monthly`), a Gateway-owned scheduler (`openclaw backup enable --every 24h`), secret redaction for remote pushes, and restore runbooks.

The proportionate answer for TermCrab is *not* Litestream. It is: make `saveConfig` atomic, write a timestamped copy into the directory that already exists, add `termcrab backup create --output <dir> --verify`, and add `termcrab restore <file>`. Under a day, and it converts a silent data-loss path into a recoverable one.

### Uninstall: absent from code and docs

There is no `termcrab uninstall`. There is no uninstall page. There is not even a "to remove TermCrab, delete these three paths" note. `grep -rn "uninstall" src/ docs/*.md README.md` returns one line, and it is about uninstalling the Play Store build of Termux (`docs/TERMUX.md:82`).

This matters more than the feature count suggests, because an install now spans four locations the user must discover unaided: the clone at `~/.local/share/termcrab`, the shim at `~/.local/bin/termcrab`, the shim at `$PREFIX/bin/termcrab`, and the state at `~/.termcrab`. Every one of them contains credentials in `config.json`. `termcrab uninstall` should print the exact paths, offer to scrub `config.json` (it holds API keys and a Telegram bot token), and support `--purge-state`.

### Migration: the one place TermCrab beats the docs

`src/migrate/openclaw.ts` plus `termcrab import` (`src/cli.ts:613`–`680`, default source `~/.openclaw` at `:630`) is a real, working importer — and OpenClaw's `/install/migrating` is about *its own* users moving between machines and importing from other agent systems, not about absorbing OpenClaw installs specifically. TermCrab's angle is sharper.

It is also invisible: `README.md` never mentions `termcrab import`, and the CLI help string (`src/cli.ts:38`–`76`) lists it without comment. Two lines of README would fix the cheapest adoption funnel in the repo.

The missing half is outbound: no documented way to move an existing TermCrab install to a new machine. Given `~/.termcrab` is plain JSON and Markdown plus a git clone, this is a two-paragraph doc, not code.

### Nodes: correctly not built, and the honest framing

OpenClaw's node system is 13 documentation pages and a large subsystem: WebSocket node hosts, nonce pairing, per-node command allowlists (`/nodes/command-policy`), node-hosted MCP servers and skills, session hosting with container isolation, file transfers, macOS widget panels, watchOS HTTPS-polling nodes, active-computer-presence routing.

TermCrab has none of it, and **that is the right call**. The reason is architectural, not budgetary: in OpenClaw, a phone is a *peripheral* that connects out to a gateway running elsewhere. In TermCrab, the phone *is* the gateway (`src/gateway/server.ts:251`), so the eight Termux:API tools run in-process with no IPC boundary (`src/agent/toolbox.ts:1209`–`:1405`). There is nothing to offload and nothing to pair. Building a node protocol would add a network hop, an auth surface, and a failure mode to a system that currently has none of those.

The gap is documentation, not code: nothing in `README.md` or `docs/ARCHITECTURE.md` explains why the two architectures differ, so a reader comparing the two docs concludes TermCrab is missing a feature rather than having made a trade.

## Loopholes and correctness bugs

Ordered by blast radius. Cross-references to `docs/gap/02-gateway.md` (auth) and `docs/gap/07-cli-and-tui.md` (CLI) are deliberate; those are not re-derived here.

1. **`README.md:60` sends users to a work branch.** `curl -fsSL https://raw.githubusercontent.com/onelitonbd/claw/**arena/01a0ec99-claw**/install.sh | bash` — while `install.sh:3` documents `.../claw/**main**/install.sh`. `arena/01a0ec99-claw` is a branch name that looks like an internal work branch with a commit hash in it. Anyone following the README installs an arbitrary snapshot, and the two documented install paths can silently diverge. Fix: one line in the README. This is the highest-harm item in the report because it is the first command a new user runs.

2. **The installer cannot actually update itself, and says so in the wrong place.** `renderUpdate` (`src/core/update.ts:83`–`:90`) says "click Auto update in the web Status screen (it installs and restarts by itself), or by hand: git pull && npm install". Three problems: (a) `applyUpdate` (`src/core/updater.ts:61`) already does exactly that pull/install/build sequence, so the manual advice is both redundant and *wrong* — it omits `npm run build`, so a user following it by hand ends up with stale `dist/`; (b) it is the only instruction, on a product whose stated primary environment is a headless phone with no browser; (c) it never mentions `install.sh`, which is the real headless upgrade path. Fix: call `applyUpdate` from `src/cli.ts:268` behind `--apply` (report 07, item 3).

3. **The loopback guard at `src/gateway/server.ts:257`–`262` is a guard against nothing.** It refuses to bind a non-loopback host unless `config.gateway.token` is set, with the message "Refusing to bind a non-loopback host without gateway.token." That reads as a security control, and `README.md:37` lists it as one ("Open ports on a LAN | Loopback by default, bearer token required, constant-time checks, non-loopback refuses to start without a token"). But **no request is ever authenticated** — `src/gateway/auth.ts` has zero importers outside `test/gateway.test.ts:43`, and `src/gateway/server.ts:709` says so in a comment. Setting a token therefore satisfies the guard and provides zero protection. Worse, `src/gateway/server.ts:1856`–`1868` goes further and logs *"panel password removed while reachable from the network — anyone on this network can use it"*, which is a fact the code then does nothing about. **This is the sharpest version of the `docs/API.md:5` / `docs/REMOTE.md:17` defect analysed in `docs/gap/02-gateway.md`**: the guard and the warning create an active false sense of security, which is worse than having neither. Until auth is restored, the guard's message and `README.md:37` must change.

4. **`termcrab skills install` writes to a directory the skill loader never reads on Windows.** `src/skills/registry.ts:174`–`:175` defines a second, local `userSkillsDir()` that shadows the canonical `src/core/paths.ts:57` version and resolves from `process.env.HOME` with a `/root` fallback. On Windows `HOME` is normally unset, so `skills install` writes to `C:\root\.termcrab\skills` (`:88` uses it) while `src/skills/loader.ts:56` reads `os.homedir()/.termcrab/skills`. On Unix the two agree only because `HOME` happens to equal `os.homedir()`. Delete the duplicate and import from `core/paths.js`.

5. **`onboard --provider <x>` is silently ignored.** `OnboardFlags.provider` is declared (`src/onboard.ts:17`), parsed (`src/cli.ts:166`), and passed through (`src/cli.ts:179`) — and then never read. Verified: `grep -n "flags\." src/onboard.ts` returns hits for `nonInteractive`, `model`, `apiKey`, `baseUrl`, `name`, `port`, `noExec`, `telegramToken`, `allowUser` and **no** `flags.provider`. `normalizeProvider` (`src/onboard.ts:155`–`:158`) hardcodes `return 'openai'` and is itself uncalled from `onboard()`. So `--provider anthropic` is accepted and discarded, and the same is true for the legacy env vars the comment at `:151`–`:154` promises still work.

6. **The documented offline quickstart cannot work.** `README.md:65`–`:67`:
   ```
   node dist/src/bin/termcrab.js onboard --non-interactive --provider mock --name Crabby
   node dist/src/bin/termcrab.js agent "hello!"        # works fully offline (mock provider)
   ```
   There is no mock provider. `src/core/config.ts:209` unconditionally sets `merged.provider.type = 'openai'` on every load, and `src/onboard.ts:69` does the same on every onboard. `grep -rn mock src/` returns only comments and the pre-0.35 transcript scrubber (`src/agent/loop.ts:70`–`:72`). The flag is also ignored (bug 5). This is the *second* install path in the README and it is dead. `src/core/friendly.ts:51` compounds it: a user hitting a network error is told "To play offline: termcrab config set provider.type mock", advice that `config.ts:209` will undo on the next load.

7. **`install.sh`'s Node gate is looser than `package.json`'s.** `:24` accepts any Node 20.x; `package.json:25` requires `>=20.10`; `src/mobile/doctor.ts:118` checks 20.10.0 correctly. Use the doctor's comparison in the installer.

8. **`TCRAB_DEST` produces a broken install with a misleading error.** See above. The shim candidate list (`install.sh:106`–`:110`) is a literal that ignores `$DEST`.

9. **`install.sh` ignores all arguments.** No `--no-onboard`, no `--version`, no `--prefix`. `bash -s -- --no-onboard` silently installs with default behaviour — the same class of bug as `termcrab gateway --help` (report 07, bug 4), and it will bite anyone writing an unattended bootstrap script.

10. **`termcrab boot rm` is a silent no-op.** `src/cli.ts:924`–`:936` handles `install` and the implicit default `status`. Any other subcommand — including `rm`, `uninstall`, `remove`, `disable` — falls through to `bootStatus()` and prints a status line with exit code 0. A user who believes they removed the auto-start script gets a cheerful `boot script: ✅ installed` instead. Add explicit `rm`/`uninstall` and make unknown subcommands error, matching the fix already queued for the CLI in report 07.

11. **`installBootScript` bakes absolute paths resolved at install time.** `src/mobile/boot.ts:20` uses `process.argv[1]`, and `:27` embeds `process.execPath` and that path into the generated script. Re-running the installer under a different `TCRAB_DEST`, or upgrading via `applyUpdate` from a different cwd, leaves a boot script pointing at the old location. The script is regenerated by `boot install`, but nothing tells the user to re-run it — `doctor` reports `boot script: ✅ installed` based on file existence (`src/mobile/doctor.ts:272`, `src/mobile/boot.ts:35`–`:36`), not on whether the embedded paths still resolve.

12. **No rollback, and the installer discards the information needed for one.** `install.sh:48` reads `CURRENT_SHA` into a variable and then never uses it. Upgrades go to whatever `main` is at that moment. `applyUpdate` (`src/core/updater.ts:70`) pulls `--ff-only` and refuses detached HEADs, which is careful, but there is no `openclaw`-equivalent rollback page, no update ledger, and no way to get back to a known-good commit from inside TermCrab. Given that `checkOnStart` defaults to `false` (`src/core/config.ts:170`), most users will only find out about a bad release when something breaks.

13. **`config-backups/` is created on every command and never written to, while `saveConfig` is non-atomic.** Covered above. The combination is the specific failure: `~/.termcrab/config-backups/` exists, so a user reasonably believes they are protected; `saveConfig` (`src/core/config.ts:216`) can truncate `config.json`; `loadConfig` (`:211`) swallows the parse error and returns `defaults()`. Result: API keys and a Telegram bot token silently gone, with a backup directory sitting empty next to the wreckage.

14. **`README.md:37` makes three security claims that are not true.** "bearer token required, constant-time checks" — `checkToken` does use `crypto.timingSafeEqual` over SHA-256 digests (`src/gateway/auth.ts:19`–`:23`), so the constant-time code is real, but it is **dead code with zero callers**; and bearer tokens are not required on any route (report 02). The third clause, "non-loopback refuses to start without a token", is true but misleading for the reasons in bug 3. Compare `docs/API.md:5` and `docs/REMOTE.md:17`, which make the same false claim in stronger form.

15. **`src/providers/probe.ts:80` documents a flag that does not exist.** The comment reads "Keyed on home so a TCRAB_HOME change (tests, `termcrab --home`) still works." There is no `--home` global flag — `main()` takes `[cmd, ...rest]` with no global parser (`src/cli.ts:144`), verified in report 07. Only the `TCRAB_HOME` env var works (`src/core/paths.ts:36`). Trivial, but it is a comment that will send someone looking for a flag that isn't there.

16. **Test-count claims in the docs are both wrong, in opposite directions.** `README.md:275` says "tests (33)". There are **46** `test/*.test.ts` files and **330** top-level `test(`/`it(` declarations (static count via `grep -rhoE "^\s*(test|it)\(" test/*.test.ts | wc -l`; this counts declarations, not executed assertions, and does not account for subtests or skips). `docs/openclaw-vs-termcrab.md:21` claims "285 tests (284 pass / 1 skip)". I did not run the suite to completion in this pass, so I am **not** asserting that 285 is wrong in either direction — I am asserting that neither number is currently substantiated, and that the README's 33 is definitely wrong because 46 files exist. Fix both by deleting the numbers, or by generating them in CI (report 09).

17. **`packages/plugin-sdk/index.ts` is not compiled, not shipped, and not imported.** `tsconfig.json` `include` is `["src/**/*.ts","test/**/*.ts"]`; `package.json:27` `files` omits `packages/`; `grep -rn "plugin-sdk" src/ test/ package.json tsconfig.json` returns nothing. Report 07 hedged on this file's contents because it had not been read. What *can* be stated without reading it: it is inert. Either delete it or add it to `include` and `files` and build a loader. Leaving an unreferenced "SDK" in the tree invites the reader to assume a plugin system exists.

18. **`supervisor` appends to `gateway.log` forever.** `src/mobile/supervisor.ts:46` opens a `'a'` write stream per gateway launch and never closes it explicitly, never rotates, and never caps size. On a phone's internal storage — the stated target — an always-on gateway that logs every request and every agent turn will eventually fill the volume. Add size-based rotation (10 MB × 3) at the `:46` call site.

19. **`docs/TERMUX.md:31` tells users to add a literal tilde to their PATH.** `echo 'export PATH=$PATH:~/.local/bin' >> ~/.bashrc` — single quotes prevent tilde expansion, so this appends a broken entry. It should be `"$HOME/.local/bin"` inside double quotes. Minor, but it is in the primary platform guide and it does not work as written.
